## 1. 분석 (실측 기반)

### 1-0. 분석 방법

- SOOP 실서버에 직접 요청을 보내 쿠키 상태별 응답을 비교했다(파이썬 `requests` 세션).
- `HTTPCookieStorage`의 동작은 macOS Foundation으로 **앱 코드를 그대로 옮겨 재현**했다.
- 앱 A/B는 **같은 빌드에 `.env`만 바꿔 넣거나, 코드 한 줄만 되돌려** 시뮬레이터에서 셀프테스트(`--soop-selftest`)로 했다.
- 타이밍에 좌우되는 경로는 **앱의 `SOOPAPIClient.swift`를 수정 없이 macOS용으로 컴파일한 하니스**로
  실서버에 붙여, 호출 순서를 통제하며 확인했다(§4-6).

### 1-1. 증상

19+ 방송을 누르면 "성인 인증이 필요한 방송입니다 / SOOP 웹에서 본인인증 + 성인 콘텐츠 보기
설정 후 다시 시도하세요" 토스트만 뜨고 재생되지 않는다. 일반 방송은 정상.

이 메시지는 커밋 `b88f41e`(2026-05-30)가 심은 것으로, 당시 결론은
**"계정의 서버측 성인 콘텐츠 상태 문제이며 클라이언트에서 우회 불가"** 였다.
이번 실측 결과 **그 결론은 오진이었다.**

### 1-2. `RESULT=-6`의 진짜 조건 — 세션 하나로 갈린다

19+ 방송 하나(`grade: 19`)에 대해 쿠키 상태만 바꿔 `player_live_api.php`(`type=live`)를 호출했다.

| 세션 상태 | 19+ 방송 | 일반 방송 |
|-----------|----------|-----------|
| 익명(쿠키 없음) | `RESULT=-6` | `RESULT=1` |
| `.env`의 `SOOP_COOKIES`만 주입 (갱신 전 값) | `RESULT=-6` | `RESULT=1` |
| ID/PW 로그인만 (미러링 없음) | `RESULT=-6` | `RESULT=1` |
| ID/PW 로그인 + `.sooplive.com`으로 미러링 | **`RESULT=1`** | `RESULT=1` |

즉 `-6`은 "계정에 성인 권한이 없다"가 아니라 **"이 요청의 세션이 19+를 볼 자격이 없다"**는 뜻이다.
갱신 전 `.env`의 `SOOP_COOKIES`는 이미 만료된 세션이었다(그 쿠키만으로 `myapi/favorite`를 부르면
`code -10000 restricted area`). 그 값이 언제 `.env`에 들어갔는지는 §1-5.

**쿠키 ablation** — 로그인이 내려준 쿠키 11종 중 FAIL 플래그인 `AbroadChk`/`AbroadVod`(§1-3에서 따로 측정)를 뺀
9종을 `.sooplive.com`에 심고 하나씩 빼고/하나만 남기며 측정:

| 조건 | 결과 |
|------|------|
| 9종 전부(FAIL 플래그 제외) | `RESULT=1` |
| `AuthTicket`만 제외 | **`RESULT=-6`** |
| 나머지 8종 중 아무거나 하나 제외 | `RESULT=1` |
| `AuthTicket` 하나만 | **`RESULT=1`** |
| 다른 쿠키 하나만 (8종 각각) | `RESULT=-6` |

→ **19+ 게이트는 유효한 `AuthTicket` 단 하나로 결정된다.** `UserTicket`의 `age`(나이 값, 공개 저장소라 가림),
`sess_adult_chk=1`, `name_chk=1` 같은 플래그는 게이트에 관여하지 않는다(계정은 이미 성인 인증 상태).
또 새 로그인은 이전 로그인의 `AuthTicket`을 무효화하지 않았다(두 티켓 모두 `RESULT=1`).

### 1-3. `AbroadChk=FAIL`은 원인이 아니었다

`b88f41e`가 지목한 `AbroadChk=FAIL`은 무관하다. 로그인 응답이 직접 `Domain=sooplive.co.kr`로 내려주는 값이다.
요청에 **실제로 실린** 쿠키로 확인했다(2026-09-26, 19+ `pms999`, 전송된 Cookie 헤더 검사):

| 보낸 Cookie | 결과 |
|-------------|------|
| 유효한 `AuthTicket`, `AbroadChk` 없음 | `RESULT=1` |
| 유효한 `AuthTicket` + `AbroadChk=FAIL`·`AbroadVod=FAIL` | **`RESULT=1`** |
| `AbroadChk=FAIL`만, 세션 없음 | `RESULT=-6` |

(셀프테스트 로그의 `abroadChk=FAIL`은 앱이 요청 직전에 FAIL을 지운 **뒤** 응답이 다시 심은 값을 찍은 것이라 근거로 쓰지 않는다.)

### 1-4. 근본 원인 — 앱이 방금 받은 로그인 세션을 스스로 덮어쓴다

세 조각이 맞물린다.

**(a) `.env` 쿠키를 4가지 도메인 형태로 주입한다** (`injectCookiesFromEnv`, 커밋 `31b8292` 기준)

```swift
for domain in [".sooplive.com", "sooplive.com", ".sooplive.co.kr", "sooplive.co.kr"] { ... }
```

1·3번째(점 있음)는 **도메인 쿠키**, 2·4번째(점 없음)는 **host-only 쿠키**로 저장소에서 서로 다른 항목이다.
host-only 항목은 `URLSession`의 쿠키 매칭에서 **정확히 그 호스트에만** 실린다. 앱의 요청은 전부
`live.`/`myapi.`/`www.`/`sch.` 같은 서브도메인이고 점 없는 `sooplive.com`·`sooplive.co.kr` 호스트로는
요청하지 않으므로(코드 grep으로 확인), 이 항목은 **앱의 API 요청에는 실리지 않는다.**
(예외: `PlayerViewController`는 도메인 구분 없이 쿠키를 모아 헤더를 직접 만든다 — §4-10)

**(b) 로그인 `Set-Cookie`는 도메인 쿠키만 덮는다.**

실제 응답 헤더에서 `AuthTicket`은 `Domain=sooplive.co.kr`(점 없음)로 내려온다.
그런데 **Foundation은 이걸 `.sooplive.co.kr`(점 있음)로 정규화해 저장한다** — 직접 확인:

```
HTTPCookie.cookies(withResponseHeaderFields: ["Set-Cookie": "...domain=sooplive.co.kr"])
  → parsed domain = '.sooplive.co.kr'
```

따라서 로그인은 `.sooplive.co.kr` 항목만 갱신하고, host-only `sooplive.co.kr` 항목은
**옛 `.env` 값 그대로 남는다.**

**(c) 미러링이 그 옛 값을 스트리밍 도메인으로 되돌려 쓴다** (`mirrorAuthCookiesToStreamingDomain`)

```swift
for c in all where c.domain.contains("sooplive.co.kr") { ...(.sooplive.com으로 복사)... }
```

`contains`는 host-only 항목도 잡는다. 결국 **새 값과 옛 값이 같은 목적지에 차례로 기록되고,
마지막에 기록된 쪽이 남는다.** 순회 순서는 보장되지 않는다.

macOS Foundation에서 앱 코드를 그대로 옮겨 재현한 결과:

```
미러링 소스 순회 순서: [".sooplive.co.kr=FRESH", "sooplive.co.kr=STALE"]
로그인 후 저장소: [".sooplive.co.kr=FRESH", ".sooplive.com=STALE",
                  "sooplive.co.kr=STALE", "sooplive.com=STALE"]
미러링 후 live.sooplive.com에 실리는 값: ["STALE"]   ← 방금 로그인한 세션이 옛 세션으로 덮였다
```

(`setCookie`의 덮어쓰기 자체는 정상이다 — 영속/세션 쿠키 조합 3가지 모두 마지막 쓰기가 이긴다.
문제는 **순서**다.) `fetchStreamInfo`는 호출 직전에 미러링을 한 번 더 하므로, 로그인 이후
모든 스트림 요청이 옛 세션을 쓴다.

같은 재현 코드로 **host-only 두 개를 주입 목록에서 빼기만 하면**:

```
로그인 후 저장소: [".sooplive.co.kr=FRESH", ".sooplive.com=STALE"]
미러링 후 live.sooplive.com에 실리는 값:      ["FRESH"]
          myapi.sooplive.co.kr에 실리는 값:   ["FRESH"]
```

### 1-7. 비번방은 무엇이 막혀 있었나 — 19+ 비번방은 `-8`

비번방 진입 자체는 직전 사이클([비번방](20260908-password-room-v1.md))에서 이미 구현돼 있다.

`.passwordRequired`를 반환해 프롬프트를 띄운다. (이번 재측정에서도 `type=live`는 빈 값/`0000`/`abcd` 어떤
비번이든 `RESULT=1 BPWD=Y`, `type=aid`는 틀린 비번에 `RESULT=0` — 직전 사이클 측정과 동일)

방 종류별로 세션 상태에 따른 `type=live` 응답을 측정했다(2026-09-26 09:02, 상위 40개 카테고리에서 유효 세션으로
라이브·`RESULT=1`을 먼저 확인한 방만, 종류마다 최대 12곳):

| 방 종류 | 표본 | 세션 없음(익명) | 유효 세션 |
|---------|------|-----------------|-----------|
| 일반 | 12 | `1` ×12 | `1` |
| 일반 비번방 | 12 | `1` ×12 (`BPWD=Y`) | `1` (`BPWD=Y`) |
| 19+ | 12 | **`-6` ×12** | `1` |
| **19+ 비번방** | 10 (라이브 전부) | **`-8` ×10** | `1` (`BPWD=Y`) |

만료 세션도 익명과 같았다(19+ `-6`, 19+ 비번방 `-8` — 각 1곳에서 확인). 즉 **`-8`은 19+ 비번방의 "로그인 필요"**다.
수정 전 앱은 `-8`을 `.notLive`로 처리해 **"방송이 종료되었거나 지금 라이브가 아닙니다"**를 띄웠다 —
비밀번호를 물어보기는커녕 방송이 끝난 것처럼 보였다. 사용자가 겪은 "비번방 진입 불가"의 실제 모습이다.
(분석 초기에는 19+ 비번방도 `-6`으로 막힌다고 **추론**해 적었으나, 측정해 보니 `-8`이었다.)

목록 표본(2026-09-24 스냅숏 — 위 표와 다른 시점, 상위 40개 카테고리 × 최대 60건, 라이브 699건, 라이브 재확인 전
목록 기준): `grade=19` 79건, `is_password=1` 31건, **둘 다인 방송 12건** — 비번방의 약 39%가 여기에 해당했다.

→ §1-4를 고쳐 유효 세션이 실리면 19+ 비번방도 `RESULT=1 BPWD=Y`로 프롬프트 경로에 들어온다.
세션이 아직 없을 때를 위해 `-8`도 `-6`과 같이 세션을 갱신해 재시도해야 한다(§2-2 #4).

### 1-8. SOOP은 무효한 `AuthTicket`을 받으면 응답에서 그 쿠키를 지운다

구현 검증 중(§4-7) 하니스로 쿠키 저장소 변화를 시간순으로 계측하다 발견했다(2026-09-25).
옛 티켓을 실은 요청의 응답이 `.sooplive.com`의 `AuthTicket`을 **삭제**한다.
(계측 출력의 요약. 오른쪽 설명은 덧붙인 것)

```
  49ms  .sooplive.com=NONE   .sooplive.co.kr=STALE   ← 옛 티켓을 실은 부트스트랩 페이지 응답이 삭제
  71ms  .sooplive.com=STALE  .sooplive.co.kr=STALE   ← 요청 직전 미러링이 옛 값을 다시 복사 → type=live 송신
 107ms  .sooplive.com=FRESH  .sooplive.co.kr=FRESH   ← 로그인 완료 + 미러링
 126ms  .sooplive.com=NONE   .sooplive.co.kr=FRESH   ← 옛 티켓으로 나간 type=live의 응답이 새 티켓을 삭제
```

의미: **로그인이 끝난 뒤에도, 그 전에 옛 티켓으로 나간 요청의 응답이 늦게 도착하면 새 세션의
`.sooplive.com` 사본이 사라진다.** `.sooplive.co.kr` 사본은 온전하다. 그래서 규칙은 하나다 —
**`live.sooplive.com`에 요청을 보내기 직전에는 미러링한다.** `fetchStreamInfo`의 첫 `type=live`는 원래 그랬고,
이번에 재시도 `type=live`·`type=aid`(§2-2 #5)와 최근 시청 폴링(#6)에도 적용했다. 미러링과 URLSession이 쿠키를
붙이는 순간 사이의 극히 짧은 창만 남는다(§4-10).

### 1-9. SOOP 로그인은 유효한 세션 쿠키가 실려 있으면 비밀번호를 보지 않는다

검증 중 "틀린 비밀번호인데 `login OK`"가 나와 확인했다(2026-09-26).

| 로그인 요청 | 틀린 비밀번호의 결과 |
|-------------|----------------------|
| 유효한 세션 쿠키를 실은 채 | **`RESULT=1`** |
| 쿠키 없이 | `RESULT=-1` |

앱 결함은 아니지만, **로그인 실패 경로를 시험하려면 만료된 쿠키 + 틀린 비밀번호**로 해야 한다(§4-4).

### 1-10. 재생 말고도 `type=live`를 보내는 곳 — HOME "최근 시청"

3차 리뷰에서 지적됐다. HOME의 "최근 시청"은 저장된 BJ들이 지금 라이브인지
`fetchLiveListForBJIDs` → `_fetchChannelMeta`(`type=live`)로 확인하고, `RESULT=1`인 것만 보여 준다.
이 폴링은 앱 시작 직후, **로그인이 끝나기 전에** 나간다. `.env` 세션이 만료돼 있으면 라이브 중인 19+ BJ가
`-6`(비번방이면 `-8`)을 받아 목록에서 빠지고, 로그인 성공 알림은 즐겨찾기만 다시 불러와서 누락된 채 남는다.
최근 시청에 19+ 1명·일반 1명을 넣고 만료 쿠키로 앱을 켜면 로그인 전 폴링은 `fetchLiveListForBJIDs(2): 1 live`다(§4-5).

## 2. 기획

### 2-1. 원칙 — "이름이 같은 세션 쿠키가 둘 이상 존재하지 않게 한다"

옛 값과 새 값이 같은 이름으로 공존하는 한, 어느 쪽이 이길지는 순회 순서에 달린 운이 된다.
**중복 자체를 없애는 것**이 고쳐야 할 지점이지, 옛 값을 뒤늦게 청소하는 것이 아니다.
여기에 더해, 세션 게이트(`-6`/`-8`)의 원인이 세션일 수 있으면 **세션을 고쳐 한 번 더** 시도해 같은 오진이
다시 생기지 않게 한다.

### 2-2. 변경 항목

| # | 내용 | 근거 |

| 1 | `.env` 쿠키를 **도메인 쿠키 2개**(`.sooplive.com`, `.sooplive.co.kr`)에만 주입 | host-only 사본은 API 요청에 안 실리면서 미러링만 오염시킨다(§1-4 a) |

### 2-3. 최종 코드에 없는 설계와 그 경위

(차수 표기: "N차 리뷰 반영"은 N차 리뷰 결과를 보고 바꾼 것이다 — §4-9의 차수별 항목과 같은 기준. 그렇게 바뀐 빌드는
N+1차 리뷰 대상이다.)

**`.env` 쿠키 삭제/복원(≈60줄)** — 처음 구현이었다. 1차 리뷰 반영으로 폐기.
- 주입 도메인 한 줄 수정으로 대체된다(§1-4 재현 코드로 동치 확인).
- 로그인 POST가 도는 동안 세션 쿠키가 통째로 비어, 동시에 진행 중인 `fetchFavorites`가 비인증 요청이 된다.
- 실측상 `UserTicket`·`RDB`·`BbsTicket`·`isBbs`는 `.env` 값과 로그인 발급 값이 같아서, 값 기준 삭제도
  로그인 발급분을 지울 수 있었다.
- 현재 프로세스가 주입한 것만 알 수 있어 **이전 빌드가 디스크에 남긴 쿠키는 못 지운다.**

마지막 항목 때문에 주입 범위 축소(#1)만으로는 기존 기기가 구제되지 않는다. 그래서 미러링 소스를
정확 일치로 좁혔다(#2) — 디스크에 남은 host-only 쿠키는 API 요청에 실리지 않고 미러링 대상도 아니게 되어,
**요청 매칭과 미러링 관점에서는 무해해진다**(§4-3에서 실제 업그레이드로 확인). 다만 `PlayerViewController`의
Cookie 헤더에는 여전히 섞인다(§4-10). 마이그레이션 코드는 두지 않았다.

**재생 전에 로그인 완료를 기다리는 게이트** — 1차 리뷰 반영으로 폐기. 로그인이 필요 없는 일반 방송까지
최대 15초 직렬로 묶인다. 앱 시작 직후의 경합은 #4의 재시도가 흡수한다(§4-6에서 실측).

**`LoginState` 4상태 + `force` 인자** — 2차 리뷰 반영으로 폐기. `login()`은 프로세스당 한 번(상태가 비었을 때)만
불리고 재로그인 경로는 항상 새 로그인을 원하므로, 캐시된 성공/실패를 돌려주는 분기에 도달하는 호출자가 없었다.
`loginInFlight` Bool + 대기열로 줄였다.

**`-6` 원인을 송신 시점 세션으로 가르는 3분기(요청 도중 로그인 완료 / 60초 넘은 세션 / 60초 이내 세션)** —
2차 리뷰의 오진 지적을 고치려고 2차 리뷰 반영으로 넣었고(3·4차 리뷰 대상), **4차 리뷰 반영으로 걷어냈다.**
이 분기가 아끼던 것은 두 가지뿐이었다: (1) 로그인이 요청 도중 끝나는 경합에서 로그인 POST 1회, (2) 성인 권한이 **없는** 계정이 19+를 누를 때마다의
로그인 POST 1회. (1)은 앱을 켜고 약 0.1초 안에 누르는 경우라 드물고, (2)는 이 앱이 쓰는 계정(성인 인증 완료)에
해당하지 않으며 그 로그인은 성공하는 로그인이라 계정 잠금 위험도 없다(틀린 비밀번호 반복은 #8이 막는다).
반면 비용은 약 16줄(상수, 락 접근자, 송신 시점 캡처 2줄, 분기 2개)과 60초라는 시간 가정, 그리고 그 가정이 만드는
오진 창이었다. 걷어낸 뒤의 경합 경로는 POST가 1회 늘 뿐 결과는 같다(§4-6의 "로그인 완료 → `-6` → 재로그인" 행).

**재시도 직전 재미러링의 경위** — 최종 코드에는 **있다**(#5). 여러 번 넣고 뺐으므로 경위를 남긴다.
- 2차 리뷰 반영: 2차 채점자가 "중복"이라 해서 뺐더니, 당시 3분기 구조의 "요청 도중 로그인 완료" 분기(로그인 없이
  곧장 재시도)에서 `-6` 응답이 새 티켓을 지워(§1-8) 재시도가 티켓 없이 나가 오진했다 — 그 분기가 일어난 **4회 모두**
  (§4-7(D)). 그래서 같은 반영 작업 안에서 되돌렸다(3차 리뷰 대상에는 있었다).
- 5차 리뷰 반영: 3분기를 걷어낸 뒤 "로그인 성공 직후라 같은 흐름에서 반복할 뿐"이라는 지적으로 다시 뺐다.
- 6차 리뷰 반영: 그 자리에 **"티켓 없이 나간 재시도를 알아보고 '다시 시도'로 안내"하는 감지 분기**(약 8줄)를 넣었다.
- 7차 리뷰 반영: 감지 분기가 잡는 삭제는 정확히 "로그인 미러링 뒤, 재시도 전"에 일어난 것이다. 그 구간에서 지워질 수 있다면
  **알아보고 실패시키기보다 1줄 미러링으로 복구하는 편이 단순하고 낫다**(리뷰 5개 차원 만장일치). 감지 분기를 지우고
  재미러링 1줄로 바꿨다. 같은 조건의 전후 실측은 §4-7(A): 최종 코드 3/3 통과, 그 1줄만 뺀 사본 3/3 오진.
- 8차 리뷰 반영: 같은 규칙을 `type=aid`에도 적용했다(재시도 응답 뒤 `fetchAID` 전에 지워지는 경우). 전후 실측 §4-7(B).
- 이 구간들이 실제 앱에서 얼마나 자주 열리는지는 모른다. §4-7의 전후 시험은 쿠키 변경 알림이나 URLSession 가로채기로
  그 구간에 삭제를 **강제한 합성 조건**이다. 실서버가 같은 삭제를 만든다는 것 자체는 §1-8에서 관측했다.

**로그인 합류(`loginInFlight`/`loginWaiters`, 약 10줄)** — 처음 구현부터 대기열(`loginWaiters`)로 있었고(2차 리뷰
반영 뒤로는 `loginInFlight` Bool + 대기열, 1~8차 리뷰 대상), 8차 리뷰 반영으로 걷어냈다. 앱 시작 로그인과 `-6`/`-8`
재로그인이 겹칠 때 POST를 1회로 합치는 장치였는데, 두 로그인이 병행돼도 두 티켓 모두 유효하므로(§1-2) 정확성에는
필요 없다. 3분기를 걷어낸 것과 같은 비용 논리로 제거했다. 대가는 두 로그인이 겹치는 경합에서 POST 1회 추가
(§4-6 `race 60` 행).

### 2-4. 하지 않는 것

- **목록에 19+ / 비번방 배지 표시** — 목록 API에 `grade`, `is_password`가 있어 가능하지만
  요청은 "시청/진입 가능"이지 표시가 아니다. 별도 사이클 후보.
- **`AbroadChk` 처리 변경** — 원인이 아님이 밝혀졌으나(§1-3), 제거 코드는 무해하므로
  동작은 그대로 두고 **틀린 주석만 실측 내용으로 교체**했다. 오진이 재발하지 않도록.
- **`PlayerViewController`의 Cookie 헤더 구성** — 도메인 구분 없이 합치는 기존 방식은 이번 범위 밖(§4-10).
- **HOME 최근 시청 폴링의 자체 재로그인** — 실행 도중 세션이 만료되는 경우까지 막으려면 `_fetchChannelMeta`가
  `-6`/`-8`을 따로 알리고 폴링 경로에도 재로그인을 넣어야 한다. 재생 경로(#4)가 이미 세션을 갱신하므로 범위를 넓히지
  않고 한계로 기록했다(§4-10).
- **`.env`에서 `SOOP_COOKIES` 줄 삭제** — 사용자의 자격증명 파일은 코드 수정의 일부로 건드리지 않는다.
  코드가 옛 쿠키를 이겨 내도록 만드는 쪽이 맞다. (그 뒤 사용자가 **쿠키 갱신을 별도로 요청**해
  값을 새 로그인 값으로 교체했다 — §5. 이 코드 수정은 그 쿠키가 다시 만료돼도 19+를 지켜 준다.)

### 2-5. 성공 판정 기준

- 19+ 방송이 **만료된** `SOOP_COOKIES`가 있는 상태에서도 재생된다.
- 19+ 비번방이 `-6`/`-8`/"방송 종료"가 아니라 비밀번호 프롬프트 경로로 들어온다 — 세션이 아직 없을 때(`-8`)도.
- 앱 시작 후(로그인 성공 뒤) HOME "최근 시청"에 라이브 중인 19+ BJ가 빠지지 않는다.
- 일반 방송·일반 비번방·로그인 실패 폴백·옛 빌드에서의 업그레이드에 회귀가 없다.
- 앱 시작 직후(로그인 진행 중/요청 도중 완료) 19+를 눌러도 계정 문제로 오진하지 않는다. 늦은 응답이 재시도나
  `type=aid` 전에 티켓을 지운 경우는 보내기 직전 미러링이 복구한다(#5, §4-7(A)(B)). 미러링과 쿠키 부착 사이의
  극히 짧은 창만 남는다(§4-10).
- 적대적 코드리뷰 확정 결함 0건, 6개 평가 항목 전부 90점 이상. (진행 상황은 §4-9 — 8차부터 **코드** 결함은
  0건이었고 확정 지적은 모두 문서 표현이었다. 최종 판정은 §4-9의 마지막 차수 결과다)

## 3. 개선 (구현)

변경 파일 3개. `fetchStreamInfo`의 본문, 6개 재생 진입부, `promptPassword`는 건드리지 않았다.

### `SOOPAPIClient.swift`

- **`injectCookiesFromEnv`** — 주입 도메인을 `[".sooplive.com", ".sooplive.co.kr"]`로 축소.
  host-only를 넣으면 안 되는 이유를 주석 1줄로 남겼다(재발 방지 — 이 문서 파일을 가리킨다. 상세는 §1-4).
- **`mirrorAuthCookiesToStreamingDomain`** — 소스 조건을 `contains("sooplive.co.kr")`에서
  `domain == ".sooplive.co.kr"`로 변경.
- **`login(completion:)`** — `credentialsUnusable`이 서 있으면 POST 없이 즉시 실패, 아니면 `performLogin`.
  - `.soopLoginSucceeded`는 `hasLoggedInOnce`가 거짓이던 **첫 성공 때만** 발송(기존에는 `performLogin` 안에서 매번).
    앱 시작 로그인이 성공하는 보통의 실행에서는 외부 동작이 같다. **달라지는 경우 하나**: 앱 시작 로그인이 일시적
    오류로 실패한 실행에서는 이후 19+ 재로그인의 첫 성공 때 알림이 나가 HOME/MY가 목록을 다시 불러온다(재생 시작과
    겹칠 수 있다). 이전에는 그 실행에서 알림이 아예 없었다(§4-10).
- **`performLogin`** — 기존 로그인 본문. 알림 발송을 위로 올렸고, **ID/PW가 없거나 서버가 `RESULT≠1`로
  거부하면** `markCredentialsUnusable()`을 부른다(네트워크·디코딩 오류는 부르지 않는다).
- **`_fetchStreamInfo`**
  - `reloginAttempted` 파라미터(재시도 1회 제한).
  - `adultGate = (RESULT == -6 || RESULT == -8)`. 재시도 전이면 `login` → 성공 시 **미러링 후** 재시도,
    실패 시 `credentialsUnusableLocked`로 거부/일시적 실패를 갈라 `.loginRequired` 또는 `.streamUnavailable(...)`.
  - 재시도에서도 막히면 `.adultVerificationRequired`.
  - `fetchAID`(`type=aid`)를 부르기 직전에도 미러링.
- **`fetchLiveListForBJIDs`** — 시작할 때 `mirrorAuthCookiesToStreamingDomain()` 호출(§1-8, §1-10).
- **`SOOPAPIError.loginRequired`** 추가, `.adultVerificationRequired` 주석을 새 의미로 갱신.
- **주석 교체** — `clearStaleAbroadFail` 문서 주석 1줄에 `AbroadChk=FAIL`이 원인이 아님을 실측 날짜(2026-09-26)와 함께
  기록(실측 내용은 §1-3), `.env` 주입부의 FAIL 제외 주석은 그 함수를 가리키는 1줄로.
- **`runSelfTest`** — `SOOP_TEST_PWD` 환경변수를 비밀번호로 전달. §4-2의 비번방 행(틀린 비번)을 앱 수준에서 재현하는 데
  필요해 남겼다. 지정하지 않으면 기존과 같다.

### `HomeViewController.swift`

### 4-8. 쿠키 동작 검증 (Foundation 재현)

### 4-10. 원격 검증 불가 / 남은 리스크

사람이 확인해야 하는 것:

- **올바른 비밀번호로 비번방 실제 재생** — 유효한 비밀번호를 가진 방이 없어 end-to-end로 확인하지 못했다.
  직전 사이클([비번방](20260908-password-room-v1.md) §4 "원격 검증 불가")도 같은 이유로 미검증이다.
  근거는 두 가지뿐이다: `type=aid`가 비번 검증 지점이라는 실측(틀린 비번 `RESULT=0`), 그리고
  정답 비번 이후 경로(`fetchAID` → `fetchViewURL` → `view_url+aid`)가 `fetchAID` 직전 미러링 1줄(§2-2 #5) 외에는
  **이번 사이클에서 바뀌지 않았고** 그 1줄을 포함해 일반 방송에서 매번 통과한다는 점(§4-2). 이번 변경으로 확인된 것은 "19+ 비번방이 프롬프트 단계까지 도달한다"까지다.
- **tvOS 리모컨 UI 상호작용** — 알림/보안 키보드 조작은 자동화할 수 없다
  (`simctl`에 tvOS 리모컨 입력 API가 없고 AppleScript 키 입력은 접근성 권한으로 차단됨).
- **계정에 실제로 성인 권한이 없는 경우의 `.adultVerificationRequired`** — 그런 계정이 없어 미검증.
  그런 계정에서 19+ 비번방이 `-6`과 `-8` 중 무엇을 주는지도 모른다(둘 다 같은 경로로 처리한다).
- **경합 경로의 앱 UI 상 재현** — 하니스(앱 코드 그대로)에서만 확인했다. 앱 UI로는 타이밍을 맞출 수 없다.
- **최종 빌드의 실기기 실행** — 설치만 했다(§5-2). 셀프테스트의 `--terminate-existing`이 사용 중인 시청을 끊거나
  다른 앱을 보던 화면을 SOOP 앱으로 바꿀 수 있어서다.

이번 설계가 기대는 전제와 그 파급:

- **미러링 소스를 `.sooplive.co.kr` 정확 일치로 좁혔으므로, 서버가 `Domain` 없이 host-only로 내려주는
  로그인 쿠키가 생기면 복제되지 않는다.** 실측 시점의 로그인 응답은 모든 쿠키에 `Domain=`을 붙였고
  Foundation이 `.sooplive.co.kr`로 정규화했다(§1-4, §4-8). SOOP이 이 형태를 바꾸면 재확인이 필요하다.
- **`-8`의 의미는 측정으로만 안다** — 19+ 비번방 10곳 모두 세션 없음이면 `-8`, 다른 방 종류 36곳에서는 한 번도 나오지 않았다(§1-7).
  SOOP이 `-8`을 다른 뜻으로도 쓴다면 그 경우에도 재로그인 1회 후 `.adultVerificationRequired`가 된다.
- **옛 빌드가 디스크에 남긴 host-only 쿠키는 삭제하지 않는다.** API 요청과 미러링에는 영향이 없지만(§4-3),
  `PlayerViewController`는 `domain.contains("sooplive")`인 쿠키를 모두 합쳐 Cookie 헤더를 만드므로
  거기에는 섞인다. 재생은 `?aid=` 토큰으로 인가되어 영향이 관측되지 않았다(실기기 1080p 재생 — §5-3,
  1회차 빌드에서 관측). 기존 동작, 범위 밖.
- **성인 권한이 없는 계정** — 19+를 누를 때마다 로그인 POST 1회(성공하는 로그인)와 `type=live` 1회가 더 나간 뒤
  `.adultVerificationRequired`가 된다(§2-3에서 받아들인 비용).
- **ID/PW 없이 `SOOP_COOKIES`만 쓰는 설정** — 세션을 갱신할 수단이 없어 `-6`/`-8`은 언제나 `.loginRequired`가 되고,
  쿠키가 유효하지만 계정 권한이 없는 경우와 구별되지 않는다. 문구가 두 원인을 모두 안내한다(#9).
- **자격증명 거부 기억의 조건** — 서버가 JSON으로 `RESULT≠1`을 주면 원인과 무관하게 거부로 보고 그 실행 동안 기억한다
  (#8의 근거). 실측으로 확인한 거부 코드는 `-1`(틀린 비밀번호)뿐이다. 다른 코드가 오면(사용자 증상) **그 실행 내내
  19+·19+ 비번방이 "로그인 세션 갱신 실패" 토스트로 끝나고**, 앱을 다시 실행해야 로그인을 재시도한다. `.env`를 고치면
  다시 빌드·설치하므로 새 실행에서 초기화된다.
- **첫 로그인 성공이 재생 중에 오는 경우** — 앱 시작 로그인이 일시적 오류로 실패한 실행에서는, 이후 19+를 눌러 일어난
  재로그인의 성공이 그 실행의 "첫 성공"이 되어 알림이 나간다. HOME/MY가 재생 시작과 겹쳐 목록을 다시 불러오고,
  MY는 포커스를 다시 잡는다. 비어 있던 목록이 채워지는 이점이 있어 그대로 두었다(§6 체크리스트에 항목 추가).
- **늦은 삭제가 남기는 창** — 앱 시작 직후처럼 로그인 전에 나간 옛 티켓 요청(HOME 최근 시청 폴링 최대 10건,
  부트스트랩 페이지, 동시에 누른 다른 카드)이 남아 있을 때, 그 응답이 재로그인 **뒤에** 도착하면 `.sooplive.com`
  티켓을 지운다(§1-8). 재시도 `type=live`와 `type=aid`는 보내기 직전에 미러링하므로 그 전에 지워진 것은 복구된다
  (§4-7(A)(B)). 남는 것은 **미러링 직후부터 URLSession이 그 요청에 쿠키를 붙이기 전까지**의 극히 짧은 창뿐이다.
  여기서 지워지면 — 재시도 `type=live`는 `.adultVerificationRequired`(오진). `type=aid`는 AID를 못 받는데, `type=live`
  응답에도 AID가 없으면 코드의 분기 순서대로 TS가 있는 방(비번방 포함)은 AID 없이 TS만 담긴 결과, TS가 없는 비번방은
  `.passwordIncorrect`, 그 밖의 방은 "재생할 수 없습니다 (no auth available)"(§4-7(B) 대조에서 관측한 증상)가 된다
  (앞의 둘은 코드 경로이며 측정하지 않음). 재현하지 않았고, 다시 누르면
  `fetchStreamInfo`가 보내기 전에 미러링하므로 복구된다.
- **HOME 최근 시청은 실행 도중 세션 만료에 대비하지 않는다.** 앱이 오래 켜져 서버 세션이 만료되면, 최근 시청 폴링은
  미러링만 할 뿐 재로그인하지 않으므로 라이브 중인 19+ BJ가 빠진다. 이때는 **Play/Pause만으로는 돌아오지 않는다.**
  19+ 방송을 한 번 눌러 재생 경로가 재로그인하게 한 뒤 Play/Pause를 누르거나, 앱을 다시 실행하면 돌아온다.
  (앱 시작 직후의 누락은 #6으로 막았다 — §4-5)
- **HOME 최근 시청의 늦은 삭제 창** — 로그인 성공 뒤 다시 부르는 폴링 직전에 미러링하지만, 그 순간 로그인 전
  폴링의 응답이 아직 오는 중이면 그 응답이 `.sooplive.com` 티켓을 지울 수 있다(§1-8). 창은 좁지만 0은 아니며,
  그 경우 Play/Pause로 복구된다(세션 자체는 유효하므로). 실측(§4-5)에서는 일어나지 않았다.

```

[Player] FAILED: ... HTTP 403: Forbidden
[Player] Fallback to view_url+aid: https://live-pcweb-kr-cdn-z02.sooplive.com/.../auth_master_playlist.m3u8?aid=...
[Player] presentationSize: 1920x1080 (1080p)
```

TS 주소 403 → `view_url+aid` 폴백으로 1080p 재생. 기존 `PlayerViewController`의 폴백 동작 그대로이며 이번 변경과 무관하다.

**주의**: 셀프테스트는 `--terminate-existing`로 앱을 재실행하므로 사용 중인 사람의 시청을 끊는다.
이를 확인한 뒤 실기기 재실행은 중단했다.

## 6. 수동 테스트 체크리스트 (실기기)

- [ ] 19+ 방송(제목/썸네일이 가려진 방송) 진입 시 바로 재생되는가
- [ ] 일반 방송이 이전과 동일하게 재생되는가 (회귀 없음)
- [ ] 19+ 비번방 진입 시 "성인 인증"·"방송 종료" 토스트가 아니라 **비밀번호 입력 알림**이 뜨는가
- [ ] 올바른 비밀번호 입력 시 재생되는가 (이번 사이클과 직전 사이클 모두 원격 미검증)
- [ ] 틀린 비밀번호 입력 시 재입력 알림이 다시 뜨는가
- [ ] 앱을 켜자마자(자동 로그인이 끝나기 전에) 19+ 방송·19+ 비번방을 눌러도 재생/프롬프트가 되는가
- [ ] 앱을 오래 켜 둔 뒤(세션 만료 가능 시점) 19+ 방송을 눌러도 재생되는가
- [ ] MY 탭 즐겨찾기의 19+ BJ도 동일하게 재생되는가
- [ ] HOME "최근 시청"에 라이브 중인 19+ BJ가 보이는가
- [ ] 19+ 재생 후 MY/HOME으로 돌아왔을 때 포커스가 누른 카드에 그대로 있는가
- [ ] (`SOOP_COOKIES`를 만료된 값으로 바꾼 `.env`로 설치하고, 네트워크를 잠깐 끊은 채 앱을 켜 시작 로그인이 실패한
      경우 — 지금 설치본의 갱신된 쿠키로는 19+가 곧바로 `RESULT=1`이라 재로그인·알림이 일어나지 않는다, §5-1)
      네트워크를 되살리고 19+를 재생한 뒤 돌아왔을 때 목록이 채워져 있고 포커스가 크게 튀지 않는가
      (§4-10 "첫 로그인 성공이 재생 중에 오는 경우")
- [ ] 즐겨찾기 목록이 정상 표시되는가

최종 빌드는 §5-2(8회차)에서 실기기에 설치돼 있다. 위 항목은 리모컨 조작이 필요해 사람이 확인해야 한다.
