# 즐겨찾기 카드 시청자수 정상화 — 2026-09-10 v1

MY 탭(및 HOME "즐겨찾기 라이브") 카드의 시청자수 배지가 현실과 동떨어진 숫자를 보여준다.
직전 사이클([썸네일 고해상도화](20260910-thumbnail-resolution-v1.md) §4-6)에서 발견해 범위 밖으로
남겼던 항목을 이번에 처리한다.

프로세스: 분석 → 기획 → 구현 → 검증 (설치는 이번 요청 범위 밖)

---

## 1. 분석 (실측 기반)

### 1-1. 증상

MY 탭 라이브 카드의 우상단 배지가 "4581.4만 시청", "14573.2만 시청"처럼 표시된다.
1.4억 명이 한 방송을 볼 수는 없다.

### 1-2. 원인: 이름이 같은 두 필드를 혼동

`myapi.sooplive.co.kr/api/favorite` 응답에는 `total_view_cnt`가 **두 군데** 있다.

| 위치 | 의미 | 예 (BJ "천양") |
|------|------|----------------|
| 항목 최상위 `total_view_cnt` | 채널 **누적** 방문자 수 | 45,813,776 |
| `broad_info[0].total_view_cnt` | **현재 방송의 시청자 수** | 1,411 |

`SOOPAPIClient.fetchFavorites`가 최상위 값을 `FavoriteBJ.totalViewCount`로 읽고 있었고,
`MyLiveBroadcastCell`이 그것을 "N 시청" 배지에 그대로 썼다.

### 1-3. 어느 쪽이 현재 시청자수인지 교차 검증

라이브 즐겨찾기 **12명 전원**에 대해 세 값을 대조했다.

```
bjId              최상위 total_view_cnt   broad_info total   pc+mobile   chapi current_sum_viewer
243000                       45,813,776              1411        1411                       1411
rkdakstlr911                145,732,009              1369        1369                       1369
hikicomoring                    743,578                35          35                         35
...                                  ...               ...         ...                        ...
```

`broad_info[0].total_view_cnt` = `pc_view_cnt + mobile_view_cnt`
= 독립 API(`chapi.sooplive.co.kr/api/<bjId>/station`)의 `broad.current_sum_viewer`.
**12/12 정확히 일치.** 최상위 값만 자릿수가 다르다.

### 1-4. `broad_info` 배열의 형태

즐겨찾기 38건 실측:
- 배열 길이 분포: `1` 12건, `0` 26건
- 라이브인데 비어 있는 경우 0건 / 오프라인인데 채워진 경우 0건

→ `is_live`와 1:1 대응하며 원소는 항상 최대 1개. `[0]`을 쓰는 것이 안전하고,
비어 있으면 0으로 떨어져 배지가 숨겨진다(기존 `> 0` 조건 그대로).

### 1-5. 다른 화면의 시청자수는 정상인가

| 화면 | 소스 | 판정 |
|------|------|------|
| LIVE 방송목록 / 탐색 / HOME 인기 / 검색 | `categoryContentsList`의 `view_cnt` | **정상** (현재 시청자수. chapi `current_sum_viewer`와 근사 일치 확인: 157 vs 164) |
| LIVE 카테고리 카드 | `categoryList`의 `view_cnt` | 정상 (카테고리 전체 시청자 합계, "N명 시청 중"으로 표기) |
| HOME 최근 시청 | `fetchLiveListForBJIDs` → **하드코딩 0** | 배지가 아예 안 뜬다. §1-6 참조 |

### 1-6. HOME 최근 시청에 시청자수가 없는 이유 (이번 범위 밖)

`fetchLiveListForBJIDs`는 `player_live_api.php`로 방송 메타를 받는데,
그 `CHANNEL` 응답(필드 96개)에 **현재 시청자수 필드가 없다**
(`CTUSER: 50000`은 채팅 정원, `SUB_PAY_CNT`는 구독 수).
그래서 코드가 `viewerCount: 0`을 넣고 있고, 배지 조건 `> 0`에 걸려 표시되지 않는다.

채우려면 BJ마다 `chapi …/station` 같은 API를 한 번씩 더 호출해야 한다 —
"잘못된 값 표시"가 아니라 "표시 안 함"이고, 요청이 늘어나므로 이번 범위에 넣지 않는다.

## 2. 기획

### 2-1. 필드를 의미대로 바꾼다

`FavoriteBJ.totalViewCount`(누적)를 **`liveViewerCount`(현재 시청자수)로 교체**한다.
필드를 추가하는 대신 교체하는 이유:

- 누적값을 쓰는 정당한 소비자가 **하나도 없다**. 이 값을 읽는 곳은 3군데뿐이고 셋 다
  "현재 시청자수"를 의도한 자리다(카드 배지, MY/HOME의 최근 시청 기록 저장).
- `totalViewCount`라는 이름 자체가 API의 오해를 부르는 이름을 그대로 가져온 것이라,
  남겨 두면 같은 혼동이 재발한다.

파싱은 직전 사이클에서 이미 `broad_info[0]`을 열고 있으므로 그 블록에 한 줄 추가한다.

### 2-2. 하지 않는 것

- HOME 최근 시청의 시청자수 채우기 — 추가 API 호출이 필요(§1-6).
- 다른 화면의 시청자수 — 실측상 정상(§1-5).

### 2-3. 성공 판정 기준

- 빌드 성공, `totalViewCount` 잔여 참조 0.
- 실데이터 기준 배지가 현재 시청자수(예: 1,411)로 표시된다.
- 적대적 코드리뷰 확정 결함 0건.

## 3. 구현

변경 파일 3개, 실질 5줄.

### `SOOPAPIClient.swift`
- `FavoriteBJ.totalViewCount` → `liveViewerCount: Int`. 두 `total_view_cnt`의 차이를
  실측 수치와 함께 doc 주석으로 남겼다(재발 방지).
- `fetchFavorites`: 기존 `broad_info[0]` 블록에서 `total_view_cnt`를 함께 읽는다.
  오프라인이면 `broad_info`가 `[]`라 자연히 0.

### `MyViewController.swift`
- `MyLiveBroadcastCell` 배지: `f.liveViewerCount` 사용.
- `playLive()`가 최근 시청에 저장하는 `LiveBroadcast.viewerCount`: `f.liveViewerCount` 사용.

### `HomeViewController.swift`
- `didSelectFavorite()`의 최근 시청 저장도 동일하게 교체.

### 4-3. 적대적 코드리뷰

2개 차원(값의 의미 / 파싱 견고성) 리뷰 → 6건 → 건별 2중 반증 검증(에이전트 14개, 전부 성공).

**이번 변경의 결함으로 확정된 것: 0건.** 확정 3건은 모두 "이 변경이 만든 결함"이 아니라
"이 변경으로 새로 가능해졌거나 드러난 것"이었고, 3건 모두 두 검증자 의견이 갈렸다(1/2).

1. **(정렬) MY 탭 라이브 그리드가 여전히 닉네임순이다.** — *수정 안 함, 후보로 기록*
   `MyViewController.swift:8`의 기획 주석이 `시청자수 내림차순 (시청자수는 모름 → 알파벳 정렬)`이라
   적혀 있다. 즉 알파벳 정렬은 "값을 모른다"는 전제의 대체안이었고, 이번 변경으로 그 전제가 깨졌다.
   실데이터로 확인한 실제 어긋남은 중간 순위에서 나온다 — 시청자수 2위(천양 1,403)가 7번째,
   3위(햇비 527)가 10번째, 4위(쿠우♪ 310)가 9번째에 놓이고 19명짜리 방송이 2번째에 온다.
   **고치지 않은 이유**: 사용자 요청은 "시청자수를 정상적으로 노출"이지 배치 변경이 아니다.
   또 시청자수 정렬은 새로고침(트리거 5개)마다 카드 순서가 바뀌어 tvOS 포커스가 이동하는
   부작용이 있어 별도 결정이 필요하다. 검증자 2명 중 1명도 같은 이유로 반증했다.
2. **(최근 시청 배지) HOME 최근 시청 카드에는 시청자 배지가 영영 안 뜬다.** — 이미 §1-6에 기록.
   리뷰가 덧붙인 사실: `loadRecent`는 저장본을 폴링 결과로 **완전히 대체**하므로
   (`HomeViewController.swift:233` `saved.compactMap { liveByBJID[$0.bjId] }`)
   `RecentWatchStore`에 저장된 `viewerCount`는 화면에 쓰이지 않는다.
3. **(무해한 무효과) 최근 시청 저장값 교체는 화면에 드러나지 않는다.** — 2번과 같은 뿌리.
   이번에 `playLive`/`didSelectFavorite`가 저장하는 `viewerCount`를 올바른 값으로 바꿨지만,
   위 이유로 **사용자에게 보이는 변화는 없다.** 값이 틀린 것보다는 맞는 게 낫기에 그대로 둔다.
   (`RecentWatchStore.Stored.viewerCount`는 사실상 write-only 필드다 — 기존부터 그랬으므로 제거는 별건)

**반증된 것 (수정 안 함)**
- *"`broad_info`의 `total_view_cnt`를 Int로만 파싱해 같은 파일의 다른 카운트보다 덜 방어적"*
  → 실측 12/12 모두 Int. 문자열로 오더라도 0이 되어 배지가 숨겨질 뿐 잘못된 값이 뜨지 않는다.
- *"`broad_info[0]`을 `user_id`/`parent_broad_no` 확인 없이 쓴다"*
  → 실측상 배열 길이는 라이브 12건 전부 1, 오프라인 26건 전부 0으로 `is_live`와 1:1이다.
- *"`fetchFavorites`가 `sanitizeJSONBytes`를 거치지 않는다"* → 기존 동작이며 이번 변경과 무관.

### 4-4. 원격 검증 불가

MY 탭 화면 자체는 확인하지 못했다 — `simctl`에 tvOS 리모컨 입력 API가 없고
AppleScript 키 입력은 이 환경의 접근성 권한으로 차단된다(직전 사이클과 동일 제약).
표시될 값은 §4-2에서 실데이터로 계산해 확인했다.
