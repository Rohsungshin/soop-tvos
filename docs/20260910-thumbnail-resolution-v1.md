# 방송 이미지 고해상도화 — 2026-09-10 v1

방송 이미지가 저해상도로 표시되는 문제. SOOP이 더 큰 이미지를 제공하는지 실측으로 확인하고,
가능한 곳을 고해상도로 교체한다.

프로세스: 분석 → 기획 → 구현 → 검증 (설치는 이번 요청 범위 밖)

---

## 1. 분석 (실측 기반)

### 1-1. 먼저 확정한 전제: Apple TV 4K는 @2x로 그린다

시뮬레이터(Apple TV 4K 3rd gen) 스크린샷이 **3840x2160**으로 캡처된다 →
UI 좌표계는 1920x1080(pt)이지만 실제 렌더링은 2배 픽셀이다.
즉 **400pt 폭 카드는 800px로 그려진다.** 소스가 그보다 작으면 그만큼 업스케일되어 뭉개진다.
(테스트 기기 "큰방"도 Apple TV 4K라 동일)

### 1-2. 라이브 썸네일(`liveimg`)의 상한은 480x270 — 더 큰 것은 없다

`https://liveimg.sooplive.com/m/<broadNo>` 기준으로 경로·쿼리·호스트 변형을 전수 시도했다.

| 시도 | 결과 |
|------|------|
| `/m/`, `/s/`, `/xl/`, `/b/`, `/t/`, `/big/`, `/large/`, `/orig/`, `/hd/`, `/n/`, `/h/`, `/mn/` | 200 · **480x270** (동일 바이트) |
| `/1280/`, `/1920/`, `/720/`, `/480/`, `/w1280/`, 크기 세그먼트 없음 | 200 · **480x270** |
| `/l/<no>` | 200 · 240x135 (**더 작음**) |
| `/o/<no>`, `<no>_1280x720`, `<no>_720`, `/m/1280x720/<no>` | 404 |
| `?w=1280`, `?width=&height=`, `?type=w1280`, `?imwidth=1280`, `?size=1280x720` | 200 · **480x270** |
| 호스트 `liveimg.sooplive.co.kr` | 200 · **480x270** (`.com`과 바이트 동일) |
| 호스트 `videoimg.sooplive.com`, `stimg.sooplive.com` | 404 |

응답 헤더에 이미지 리사이즈 CDN(Akamai IM / Naver type 등)의 흔적이 없다.

**8개 카테고리에서 73개 라이브 방송을 표본 추출해 실제 응답을 측정한 결과**:

| 해상도 | 건수 |
|--------|------|
| 480x270 | 71 |
| 960x540 | 2 |

960x540 2건은 **두 방송의 MD5가 완전히 동일**(`03fe3fd2…`, 49005B)했다. 이미지를 열어 보니
**19+ 방송 가림용 고정 일러스트**다. 실제 방송 프레임이 아니다.

→ **결론: 라이브 방송 썸네일은 480x270이 상한이다. 코드로 개선 불가.**
카드 이미지 영역 400x225pt(=800x450px)에 대해 1.67배 업스케일이 남지만 소스가 없다.

### 1-3. 프로필 이미지: 앱이 **일부러 100px짜리 썸네일**을 쓰고 있었다

앱이 만들던 URL은 `stimg.sooplive.com/LOGO/<앞2자>/<bjId>/**m**/<bjId>.webp` 인데,
경로의 `/m/`이 **100px 폭 소형 썸네일**을 가리킨다. 빼면 원본이 나온다.

**BJ 110명 표본 측정:**

| 항목 | 결과 |
|------|------|
| 원본 URL 응답 성공 | **108/110** |
| 실패 2건(`ititit`, `kysvic2`) | `.webp` / `.jpg` / `/m/` **모두 404** — 프로필 자체가 없는 BJ (기존 코드도 못 보여줬다) |
| 폭 배율 (원본 ÷ `/m/`) | 중앙값 **4.20x**, 최소 1.00x, 최대 10.80x, 동일한 경우 3/102 |
| 원본 바이트 | 중앙값 18KB, 평균 248KB, 최대 1.86MB |
| `.jpg` 바이트 | 중앙값 **245KB**, 평균 729KB, 최대 2.08MB |
| 확장 webp(VP8X, 애니메이션 가능) | 47/110 |
| `.webp` URL인데 실제 내용이 GIF | 6/110 (1.4~1.9MB) |

→ **원본 webp가 해상도는 중앙값 4.2배 크면서 바이트는 jpg의 1/13이다.** webp를 쓰는 것이 맞다.
(`.webp` URL로 GIF가 오는 6건도 `UIImage(data:)`가 첫 프레임을 디코드하므로 문제없다)

### 1-4. MY 탭 라이브 카드는 라이브 썸네일을 **한 번도 받은 적이 없다**

`MyViewController`가 만들던 URL:
```
https://liveimg.sooplive.com/m/<bjId>?bucket=...
```
`liveimg`는 **broadNo로만 키가 잡힌다.** bjId를 넣으면 404다 — 라이브 중인 BJ 5명 전원 404 확인.

즉 이 요청은 **항상 실패**하고 "실패 시 프로필로 fallback" 경로로 떨어져,
MY 탭 라이브 카드는 **언제나 100x133 세로 프로필 사진**을 보여 왔다.
HOME "즐겨찾기 라이브" 캐러셀도 같은 셀(`MyLiveBroadcastCell`)이라 동일하다.

이것이 체감 "너무 저해상도"의 가장 큰 원인이다 —
**380x213pt(=760x426px) 자리에 100x133 → 폭 7.6배 업스케일**,
게다가 세로 사진을 가로 카드에 `scaleAspectFill`하느라 위아래가 크게 잘린다.

### 1-5. 즐겨찾기 API가 이미 방송 썸네일 URL을 준다 (`broad_info`)

`myapi.sooplive.co.kr/api/favorite`의 각 항목에는 `broad_info` 배열이 있다.
오프라인이면 `[]`, **라이브면 현재 방송 정보가 들어 있다**:

```json
"broad_info": [{
  "user_id": "hikicomoring", "broad_no": 297012517,
  "broad_img": "//liveimg.sooplive.co.kr/h/297012517.jpg?29816951",
  "broad_title": "...", "total_view_cnt": 35, "broad_resolution": "1920x1080",
  "is_adult": false, "is_password": false, ...
}]
```

- `broad_img`가 가리키는 이미지는 `liveimg.sooplive.com/m/<broadNo>`와 **바이트가 완전히 동일**하다
  (MD5 대조). 즉 480x270 실제 방송 썸네일이다.
- 쿼리의 캐시버스터(`?29816951`)는 **모든 BJ가 공유하는 1분 단위 시간 버킷**이다
  (9초 간격 3회 호출 동안 값이 고정, 다음 분에 +1). 같은 분 안에서는 URL이 안정적이라
  이미지 캐시가 그대로 적중하고, 최대 60초 지난 프레임이 보장된다.
- Referer 없이도 200으로 받아진다 — 앱의 `URLSession.shared` 조건과 동일하게 확인.

→ **추가 네트워크 요청 0으로 실제 방송 썸네일을 쓸 수 있다.**

> 이 사실은 처음 분석 시점(00:1x KST)에 확인하지 못했다. 그때는 이 계정의 즐겨찾기 38명 중
> 라이브가 0명이라 `broad_info`가 전부 `[]`였다. 검증 단계에서 라이브 3명이 생겨 확인했고,
> 그 결과 기획을 더 단순한 쪽으로 바꿨다(§4-3).

### 1-6. 그 외 이미지 소스

| 대상 | 소스 해상도 | 표시(pt) | 필요 px(@2x) | 판정 |
|------|------------|---------|-------------|------|
| 카테고리 카드 (`admin.img.sooplive.com/category_img/…`) | **300x400** (세로 포스터) | 320x170 | 640x340 | `_org`/`_l`/`?type=` 변형 전부 404 또는 동일. **개선 불가**. 게다가 세로 원본을 가로 영역에 맞추느라 세로의 절반 이상이 잘린다 |
| 플레이어 pre-roll 포스터 | 480x270 | 580x326 | 1160x652 | 라이브 썸네일 상한과 동일. 블러가 덮여 있어 체감 영향 적음. **개선 불가** |
| 방송 카드 (LIVE/방송목록/탐색/HOME 인기/검색/최근시청) | 480x270 | 400x225 | 800x450 | **개선 불가** (§1-2) |

### 1-7. 요약

**고칠 수 있다**
1. MY/HOME 즐겨찾기 **라이브** 카드: 100x133 프로필 → 실제 방송 썸네일 480x270 (+ 세로 크롭 해소)
2. 프로필 이미지 전반: 100px `/m/` 썸네일 → 원본 webp (폭 중앙값 4.2배)

**고칠 수 없다 (소스 한계 — §1-2 / §1-6)**
- 라이브 방송 썸네일 480x270, 카테고리 이미지 300x400, 플레이어 포스터

## 2. 기획

### 2-1. 프로필 이미지 URL을 한 곳으로 모으고 원본을 쓴다

두 셀이 각자 URL 문자열을 조립하던 것을 `SOOPAPIClient`의 static 헬퍼 하나로 모은다.

```swift
/// 경로의 `/m/`은 100px 소형 썸네일 — 원본(webp)을 쓴다.
static func profileImageURL(bjId: String) -> URL?
```

### 2-2. 즐겨찾기 응답의 `broad_img`를 그대로 쓴다 (추가 요청 0)

- `FavoriteBJ`에 `thumbnailURL: URL?`을 추가하고, `fetchFavorites`가 `broad_info[0].broad_img`를
  파싱해 채운다. 프로토콜 상대 URL(`//liveimg…`)이라 `https:`를 붙인다.
- 셀은 `f.thumbnailURL`이 있으면 그것을, 없거나 로드 실패면 §2-1의 고해상도 프로필을 쓴다.
- **404가 확정된 bjId 기반 `liveimg` 요청은 제거한다** — 낭비되던 요청도 함께 사라진다.
- URL을 앱이 추측하지 않고 서버가 준 값을 쓰므로, 경로 규칙이 바뀌어도 따라간다.
- 캐시버스터가 1분 버킷이라 새로고침을 연달아 해도 카드가 깜빡이지 않는다(§1-5).

### 2-3. 하지 않는 것

- 라이브 썸네일/카테고리/포스터 해상도 — 소스 상한이라 코드로 개선 불가(§1-7).
- 이미지 업스케일 필터·캐시 한도 조정 — 근거 없는 튜닝.
- 카드 크기 등 디자인 변경 — 범위 밖.

### 2-4. 성공 판정 기준

- tvOS 시뮬레이터 Debug 빌드 성공.
- MY/HOME 즐겨찾기 라이브 카드가 480x270 방송 썸네일을 쓴다. 404 요청 소멸. 추가 요청 0.
- 모든 프로필 이미지 요청이 `/m/` 없는 원본 URL이다.
- 적대적 코드리뷰에서 확정된 회귀 0건.

## 3. 구현

변경 파일 3개.

### `SOOPAPIClient.swift`
- `FavoriteBJ`에 `thumbnailURL: URL?` 추가.
- `fetchFavorites`가 `broad_info[0].broad_img`를 파싱(프로토콜 상대 URL에 `https:` 부착).
  오프라인이면 `broad_info`가 `[]`라 자연히 `nil`이 된다.
- `static func profileImageURL(bjId:)` 추가 — `/m/` 없는 원본 webp. 실측 근거를 주석에 남겼다.
- 기존 `liveimg` URL 조립 2곳(`fetchLiveListForBJIDs`, `fetchLiveList`)은 이미 broadNo 기반이라 그대로.

### `MyViewController.swift`
- `MyLiveBroadcastCell.configure(with:)` — 항상 404였던 bjId 기반 요청을 제거하고
  `f.thumbnailURL` → 실패 시 고해상도 프로필 순으로 로드.
- `MyOfflineBJCell.configure` — 손으로 조립하던 `/m/` webp URL을 `profileImageURL`로 교체.

### `HomeViewController.swift`
- 변경 없음(같은 셀을 쓰므로 자동 적용). 실제로는 검증 중 되돌린 2단계 로드 코드만 제거됐다(§4-3).

### 의도적 비변경
- 라이브 방송 썸네일 / 카테고리 이미지 / 플레이어 포스터 — 소스 상한(§1-2, §1-6).

## 4. 검증

### 4-1. 빌드
tvOS 시뮬레이터(Apple TV 4K 3rd gen) Debug 빌드 — 변경 단계마다 총 4회 **BUILD SUCCEEDED**.

### 4-2. 실서버 실측

- `broad_info[0].broad_img`로 라이브 즐겨찾기 3명의 썸네일을 받아 **전부 480x270** 확인
  (297012517 / 297009801 / 297012819).
- `broad_img`와 `liveimg/m/<broadNo>`가 **바이트 동일**(MD5 대조).
- **Referer 없이도 200** — 앱의 `URLSession.shared`와 같은 조건에서 라이브 썸네일·프로필 모두 로드됨.
- WebP 디코딩: ImageIO가 `org.webmproject.webp`를 지원하고 420x559로 디코드됨을 직접 확인.
  tvOS 17도 동일한 ImageIO를 쓴다.
- 변경 전 이 자리 이미지는 100x133 프로필이었다 → **폭 4.8배, 픽셀 수 약 23배**, 세로 크롭 해소.

### 4-3. 적대적 코드리뷰 (워크플로) → 기획 자체를 단순화

4개 차원 리뷰 → 18건 → 건별 2중 반증 검증(에이전트 40개 중 26개는 세션 한도로 실패,
findings 6~18은 **미검증**으로 남아 아래에 직접 판정했다).

리뷰가 지적한 것 중 확정 4건은 **모두 첫 구현의 "2단계 broadNo 해석" 설계에서 나온 것**이었다:
썸네일 맵이 merge-only라 이전 방송 프레임이 남을 수 있음, 랜덤 캐시버스터 탓에 새로고침마다
카드가 비어 보임 등. 이 지적을 반영하려던 중 §1-5의 `broad_info`를 실측 확인했고,
**추가 요청 0짜리 더 단순한 방법이 있음이 드러나 2단계 설계 자체를 폐기**했다.
그 결과 확정 4건이 전부 소멸했다(맵도, 2단계도, 병합 로직도 없어졌다).

리뷰 지적 중 **실측으로 반증한 것**:
- *"`liveimg`가 480x270 상한이라는 §1-2는 거짓 — 약 28%가 960x540을 준다"*
  → 73개 표본 중 960x540은 2건(2.7%)뿐이고, 그 2건은 **MD5가 동일한 19+ 가림 일러스트**였다.
  실제 방송 프레임은 전부 480x270. §1-2 유지.
- *"원본 webp가 없는 BJ가 있어 카드가 아예 비게 된다"* (2/2 확정이었음)
  → 110명 표본에서 원본이 없는데 `/m/`은 있는 경우 **0건**. 실패 2건은 세 변형 모두 404인
  "프로필 자체가 없는 BJ"로, 변경 전에도 못 보여줬다. **회귀 아님.**
  (파서가 못 읽은 6건은 `.webp` URL로 GIF가 오는 경우로, `UIImage`가 정상 디코드한다)
- *"`/m/` 대비 폭 이득은 중앙값 1.5배에 불과하다"* → 실측 중앙값 **4.20배**. 문서 쪽이 보수적이었다.

### 4-4. 시뮬레이터 실행

앱 설치·실행 3회. 정상 렌더링, 크래시 없음, `fetchFavorites: 38 (3 live)` 확인.
HOME 상단 스크린샷으로 회귀 없음 확인.

### 4-5. 원격 검증 불가 / 확인 못 한 것

- **MY 탭과 HOME "즐겨찾기 라이브" 행의 실제 화면을 보지 못했다.** 두 화면 모두 리모컨 조작
  (탭 이동/스크롤)이 필요한데, `simctl`에는 tvOS 리모컨 입력 API가 없고 AppleScript 키 입력은
  이 환경의 접근성 권한으로 차단된다. 데이터 경로는 §4-2에서 실서버로 확인했다.

### 4-6. 확인했으나 이번 범위에서 고치지 않은 것

- **MY 카드의 시청자수가 잘못된 값이다.** `FavoriteBJ.totalViewCount`는 응답의 `total_view_cnt`
  (= 채널 **누적** 방문자, 예: 743,578)를 쓰고 있어 카드에 "74.4만 시청"으로 표시된다.
  현재 시청자수는 `broad_info[0].total_view_cnt`(예: 35)다. 이미지 문제와 무관해 손대지 않았다.
- 즐겨찾기에서 재생할 때 플레이어 pre-roll 포스터가 비어 있다
  (`didSelectFavorite` / `playLive`가 `posterThumbnailURL`을 넘기지 않는다).
  이제 `f.thumbnailURL`이 있으니 한 줄로 채울 수 있다.
- 프로필 원본 중 일부는 1~2MB 애니메이션(webp/GIF)이고 앱은 첫 프레임만 쓴다.
  캐시되므로 1회성이지만, `ImageCache`의 디코드 기준 비용은 `/m/` 대비 크게 늘어난다
  (100x133 ≈ 53KB → 420x559 ≈ 940KB). 50MB 한도에서 퇴출이 잦아질 수 있다.
- 카테고리 카드는 남은 것 중 가장 심한 업스케일(300x400 → 640x340, 세로 절반 이상 크롭).

## 5. 수동 테스트 체크리스트 (실기기)

- [ ] MY 탭 **라이브** 카드에 BJ 프로필 사진이 아니라 **실제 방송 화면**이 나오는가
- [ ] MY 탭 **오프라인** 카드의 프로필 사진이 이전보다 또렷한가
- [ ] HOME "즐겨찾기 라이브" 캐러셀도 동일하게 방송 화면이 나오는가
- [ ] 새로고침(Play/Pause)을 반복해도 카드 이미지가 깜빡이지 않는가
- [ ] 프로필 이미지가 없는 BJ의 카드가 깨지지 않고 회색 placeholder로 남는가
- [ ] 프로필이 애니메이션인 BJ의 카드가 정지 이미지로 정상 표시되는가
- [ ] MY 탭 로딩 속도가 이전과 같은가 (추가 요청이 없으므로 동일해야 한다)
- [ ] 방송 목록/LIVE/탐색/검색 카드 이미지가 이전과 동일한가 (회귀 없음)

설치(실기기 배포)는 이번 요청 범위 밖 — 별도 진행.
